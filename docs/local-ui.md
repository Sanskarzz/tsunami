# Local operator interface

The embedded frontend reads the configured-application APIs. Activity, findings and outcomes come from the control plane; no sample finding, fictional counter or simulated running state is inserted. [Verification](verification.md) separates local source/browser checks from the historical Kubernetes journey and current readiness.

The [onboarding flow](application-onboarding.md) provides initial details, checked missing-information questions, protected bearer access, bounded prerequisite validation and a saved draft. It uses rules, not a live-model setup planner.

The UI supports synthetic object/property plans, exact scope approval, a keyed scripted attempt, actual activity/status, Stop, saved-history recovery, explicit evidence inspection/download and fresh-scope linked retest. Password/SSO/MFA login, arbitrary requests, live application inference, customer accounts and human-review submission are unsupported.

## Enable and open

Follow the [Getting Started](getting-started.md) for idle-work checks, explicit fixture refresh/build, loopback port-forwarding and private operator-token connection. The sole UI entry point is `/ui/`; it refuses non-loopback Host values and credentials/query parameters in UI URLs. This is an exposure guard, not authentication or protection from a compromised workstation.

`make ui-deploy` opts the existing control deployment into `TSUNAMI_ENABLE_UI=true`, preserving its onboarding key/configuration/history and selecting matching native/tools images. It adds no public ingress or customer sign-in. A replacement build needs fresh qualification. The token remains in page memory only and must be entered privately before screen sharing.

## Screens and API calls

| Screen/action | Existing operator API | Decision |
|---|---|---|
| Connect / refresh lists | `GET /v1/applications`, `GET /v1/engagements`, `GET /v1/onboarding`; Connect also reads `GET /v1/status` | Tenant-authenticated registered plans and history only. Route status is startup configuration, not a live dependency probe. |
| Choose application | None | Local selection; no target requests. |
| Create draft | `POST /v1/engagements`, then `GET /v1/engagements/{id}` | Server snapshots the registered application and limits. |
| Approve | `POST /v1/engagements/{id}/approve` | Server records approval of immutable scope. The checkbox is bound to the displayed digest; no digest typing is required. The backend requires this reviewed `scope_digest` and rejects missing/mismatched values. |
| Start | `POST /v1/engagements/{id}/runs` | Sends one keyed scripted action; explicit same-key recovery identifies the same run. Reconciliation creates/observes its Job. |
| Observe | `GET /v1/engagements/{id}`, `GET /v1/runs/{run}/status`, cursor-based `GET /v1/runs/{run}/events` | Read-only status and bounded actual activity metadata. No capture bodies are polled. |
| Stop assessment | `POST /v1/engagements/{id}/stop` | Durable engagement revocation and cancellation; drain/exit/cleanup are separate facts. |
| Open Evidence / refresh findings | `GET /v1/engagements/{id}/findings` | Body-free candidate/check/capture metadata; no automatic full export or raw inspection. |
| Inspect one capture | `GET /v1/engagements/{id}/evidence/{E-sha256}` | Explicit raw artifact read; verify bytes and provenance before display. No target replay. |
| Load full export | `GET /v1/engagements/{id}/export` | Separate explicit snapshot including raw synthetic responses and existing candidates/reviews. |
| Create linked retest draft | `POST /v1/engagements` with `source_engagement_id` and explicitly selected registered application | New unapproved scope with its own access bindings; no copied approval/credentials or automatic Start. |
| Compare source/retest | `GET /v1/engagements/{retest-id}/retest` | Read-only scope differences, compatibility, latest actual outcomes and selected artifact references. No raw bodies/target replay. |
| Download | No new request after inspecting an artifact or loading an export | Original artifact bytes, bundle JSON or draft Markdown. |

The API explorer shows actual operator HTTP calls made by **this tab**, with method/path, body, response status and duration. Authorization is omitted. Full exports and single raw artifacts are summarized in that explorer; raw evidence is available only in its explicit viewer/download. It is not a trace of internal controller decisions, broker tool calls, target packets or another terminal's API calls. Broker captures and recorded status/events provide those separate observations. Target/tool traffic never comes from the frontend.

The planned seven reads are shown before execution, with their purpose. Full public scope/prerequisite assertions are available for review. The result and baseline verification count come from the trusted validator. `confirmed` produces a candidate requiring review; `no_issue_observed` is limited to the selected test; `inconclusive` and Stop do not mean secure. This UI creates no review or severity rating. Matching previously recorded reviews retain their actual provenance/rating in finding metadata and downloads; automated lab review is not human signoff.

Registered applications, scope approval records and latest attempt outcomes are separate labels. Access is described as locally configured/unavailable/changed, with current session health unknown; setup permission expiry and historical baseline validation are labeled separately. No access check is performed by reading metadata.

The stored-attempt policy panel uses the run's recorded allowance, not the current profile default. Missing metadata has no hardcoded budget fallback. Failed status refreshes retain the last snapshot with a stale marker; an executor-check attempt is not proof of a successful worker observation. Start is disabled for missing/disabled scope metadata or locally unavailable access, while Stop remains independent. Backend admission remains authoritative even if a client bypasses these UI guards.

Acknowledgement never means drain, worker exit or cleanup. A late response cannot clear the receipt. Dashboard uses real registrations and the [stored latest-attempt projection](engagements.md#dashboard-list-metadata), separating scope approval from attempt state/verdict. Access configuration/observations are expandable; current credential health stays unknown. Add Application distinguishes a new integration from reuse of exact lab facts/credentials, with missing facts handled by checked questions. Readable preflight and assessment tables show the actual account/GET/path pairs, addresses, intended rule, limits and expiry. Setup revision/digest changes clear preflight review; scope changes clear assessment review. Registration, preflight, approval and Start remain separate.

The normal journey requires no JSON editing, manual fingerprint typing or Kubernetes operation. API/architecture inspection and raw scope/assertions/fingerprint are collapsed by default. Read the primary scope, check the explicit permission box and approve. The reviewed fingerprint is submitted as `scope_digest` and checked against the saved scope inside the server approval transaction. Unsupported procedures disable approval/Start. Scope exclusions and synthetic-evidence handling remain visible.

Missing checks or unresolved earlier exposures remain visible; an unrelated later denial does not replace the selected earlier exposure.

## Failures and browser boundary

- The operator token is held in page memory only. No cookies, local/session storage, arbitrary control origins, proxy service or saved browser login are added. Onboarding has separate masked bearer fields with encrypted backend storage; those inputs are omitted from conversation/API explorer bodies. A page reload/disconnect requires reconnection. Browser extensions, DevTools and the trusted workstation can still access memory; this is not protection against a compromised browser.
- The opt-in wrapper sets `Cache-Control: no-store` and the UI has a same-origin CSP with no external scripts/fonts. Target/API text and Markdown are rendered as text, not HTML. Evidence can still contain sensitive echoed values; general redaction remains unfinished. Treat raw evidence/downloads accordingly.
- Draft/approve/start/Stop are never automatically retried. A lost Start response may already have created work. Refresh reads its stored child IDs, or explicit **Recover Start** resubmits the exact original action key/request. The server atomically returns the same run; conflicting key reuse fails. The key remains in page memory and is cleared on disconnect; after reload use history to recover existing work. Duplicate clicks remain blocked while a request is pending, and new explicit attempts still require new keys and normal backend limits. Start/recovery responses contain metadata/public scope, never raw evidence.
- Stop is available independently of a pending Start/export/observation request. A failed acknowledgement is shown as unconfirmed. An acknowledged Stop followed by a failed read is not called a cleanup success. No external emergency egress cutoff is added.
- Manual/polled observation shares one in-flight refresh, with separate status/feed errors and bounded cursor pages. It ends on errors, pause, leaving the execution screen, selection changes, disconnect, 120 refreshes, a stopped empty scope, or observed cleanup with known zero local/uncertain work and no unread page. Explicit Resume restarts read-only observation. Cancelled/late viewer reads cannot overwrite the new selection or Stop receipt. Disconnect remains available during pending actions; it cancels reads, invalidates late responses and never sends Stop. Observations may be stale; API object absence is not process-exit proof.
- The viewer uses the existing 192 MiB inline export ceiling. Large exports can consume significant browser memory; this is a small lab interface, not scalable evidence storage/delivery. Downloads are JSON/Markdown, not an automatically materialized evidence directory. Use `tsunami export-bundle --input FILE --out NEW_DIRECTORY` to materialize and run the existing verifier.

## Qualification

The selected-deployment driver is `make verify-ui-demo`; `make demo-rehearse` adds scheduled 0/30/90/150/200/255-second stages and a 300-second finish. The former does not prove a timed rehearsal. The full campaign checks deployed asset hashes and creates six fresh owned assessments: real onboarding/finding, active held-request Stop during a pending viewer export, a linked fixed-app retest with lost Start recovery, and three separate property controls. The property controls run after the timed presentation. Actual journal sequences, validator-selected artifacts/download hashes, target cancellation/counters, fresh approval, preserved original evidence and same-origin behavior are checked. The onboarded worker is inspected through CRI for actual gVisor/runtime/image identity.

Builds, credential preparation and native/curl network checks are separate qualification steps; see [configuration](demo-configuration.md). The [retained campaign](../examples/demo-journey/README.md) is an automated paced browser dry run with a presenter script, not recorded human narration or a guarantee for future response times. It ended with eight engagement slots. Recheck credentials/capacity; the full campaign requires seven free slots for six assessments; never discard history to make it fit. The three-assessment live presentation and the property campaign remain distinct owned scopes. The canonical guide also documents a core-only rehearsal that explicitly excludes property qualification. Private full records live under `artifacts/ui/browser-.../`; only a reviewed selection is retained under `examples/demo-journey/`.

`make verify-ui-retest` runs all **38 frontend tests**, adding fresh-review gating, real comparison presentation, incompatible/unfinished outcomes, explicit destination/source submission, lost draft recovery, stale/mismatched reads, safe text, Stop and disconnect independence. `make verify-ui-retest-browser` checks two real native Mecatl attempts across distinct owned origins: a confirmed source, source revocation, linked changed-target draft, separate approval/Start, no-issue retest and preserved original candidate/artifact bytes. It also checks an unexecuted incompatible draft, Dashboard recovery without replay, metadata-only navigation and narrow layout. Go asserts fourteen target reads/two probes and no unexpected paths. Requires Go, Node 22 and Chrome; private records live under `artifacts/ui-retest/local-.../`. This is disposable source integration, not Kubernetes/gVisor/Cilium qualification.

`make verify-ui-findings` runs all **30 frontend tests**, including prior metadata/activity/onboarding coverage plus explicit raw-read integrity, download bytes, safe text, missing/stopped evidence, stale/late reads and Stop/disconnect independence. `make verify-ui-findings-browser` runs five real native Mecatl controls against disposable object/property targets: leak, denial, property leak, filtering and ambiguity. Go asserts 35 reads/five probes and no unexpected paths; Chrome checks metadata-only navigation, exact validator links, explicit owner/probe artifacts, original-byte downloads, full-export correspondence, review provenance, narrow layout and same-origin behavior. It requires Go, Node 22 and Chrome and saves private records under `artifacts/ui-findings/local-.../`. This uses `LocalScheduler`, not Kubernetes isolation, and calls no model.

`make verify-ui-onboarding` runs all 23 frontend tests. `make verify-ui-onboarding-browser` checks the real Add -> explicit four-read preflight -> unapproved draft -> reviewed approval -> Start path, with target-side counts and the existing fixed curl adapter. Negative checks cover invalid operator tokens, missing API, unsupported password/SSO, changed setup review, stale grant rejection without traffic, protected-input omission, exact scope rendering, text injection, Dashboard state/result separation and narrow layout.

The onboarding browser check requires Linux, Python 3, `bwrap`, Go, Node 22, Chrome and curl. Its test-only launcher mounts the exact reviewed script at its fixed `/opt/tsunami/http-read.sh` path in a temporary filesystem view for the Go fixture/worker. It installs nothing on the host and adds no configurable worker script path. Chrome retains its normal host sandbox outside that view; its temporary profile is passed only to the test driver. This is not a Kubernetes/worker-containment qualification. Private summaries/screenshots live under `artifacts/ui-onboarding/local-.../`; temporary fixture state/profile are cleaned up.

`make verify-ui-activity` runs 18 isolated frontend tests, including concurrency and failure injections. `make verify-ui-activity-browser` is an opt-in Go/Chrome integration test using a temporary database, disposable loopback bearer/JSON targets, and the real control plane, broker, validator and scripted Mecatl `LocalScheduler`. It makes five explicitly approved attempts: vulnerable/fixed outcomes (including explicit same-key Start recovery) and three active held-request Stops during pending export/Start and a lost Stop response. Go asserts target holds/cancellations and no remaining active work. It also checks journal-to-screen sequences, read-only recovery, same-origin requests and narrow layout. Node 22 and Google Chrome are required; ordinary `make verify` skips this optional browser test.

The local browser test saves private summaries/source asset hash/screenshots under `artifacts/ui-activity/local-.../` and cleans up its temporary browser profile/database/targets. It changes no cluster, fixture configuration or selected history and calls no model. It establishes source/UI integration, **not Kubernetes/gVisor/Cilium isolation**. Failure injection delays/drops real responses; it never supplies fake findings/events to the frontend. The existing deployment driver below remains a separate qualification and needs matching rebuilt assets/server, current credentials and capacity.

The Kubernetes browser driver requires local Node 22 with WebSocket support and Google Chrome. It uses a fresh temporary headless profile, the owned cluster and a loopback port-forward. It reads the lab token into process/page memory without printing it. It automatically approves **owned-lab** scopes, inspects real results, downloads/materializes evidence, checks hashes, and tests invalid tokens, wrong digests, duplicate clicks, display injection and narrow-screen layout. It simulates a lost response after committed Start and holds a real export response while Stop is used. These are client-side failure injections, not production partitions. The legacy no-flag/`--onboarding` modes retain their three/four-assessment campaigns; the timed mode uses `--demo --rehearse`. Each creates new history and attempts to Stop only its own engagements. No customer application or external model is contacted. A forced kill/platform failure can still leave uncertain work; inspect it before maintenance.

It saves a private result under `artifacts/ui/browser-.../`, including screenshots, IDs/status, credential-free operator request metadata, downloads and materialized exports. The display-injection check modifies only a browser-side application-list response; it does not fabricate target evidence. Failed records remain failed. Review output for credentials/data before sharing. This does not qualify arbitrary hostile shell execution, all browsers, accessibility, distributed failures, scale or real customer readiness.
